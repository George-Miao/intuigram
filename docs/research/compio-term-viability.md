# Compio terminal I/O viability

Initial research snapshot: 2026-08-02

## Conclusion

`compio-term` is viable as a reusable Unix-first crate. Compio 0.19.1's `PollFd` exposes an awaitable `read_ready` operation and stores the in-flight one-shot poll in the descriptor wrapper, so a terminal-input future can suspend without a timer or helper thread ([Compio `PollFd`](https://github.com/compio-rs/compio/blob/d7387fc16e143ded604b7c18ea3c1e95745028aa/compio-runtime/src/fd/poll_fd/mod.rs), [Unix implementation](https://github.com/compio-rs/compio/blob/d7387fc16e143ded604b7c18ea3c1e95745028aa/compio-runtime/src/fd/poll_fd/unix.rs)). On Linux the resolved Compio driver can submit the readiness operation as `IORING_OP_POLL_ADD`; its portable Unix driver expresses the same operation as a one-shot readable-fd wait ([io_uring operation](https://github.com/compio-rs/compio/blob/d7387fc16e143ded604b7c18ea3c1e95745028aa/compio-driver/src/sys/op/general/iour.rs), [poll-driver operation](https://github.com/compio-rs/compio/blob/d7387fc16e143ded604b7c18ea3c1e95745028aa/compio-driver/src/sys/op/general/poll.rs)).

Compio-native output is viable too, but the asynchronous boundary should be a whole output batch, not Crossterm's `Command` trait. Keep `Command` as a synchronous ANSI encoder, collect a frame into a reusable owned byte buffer, then `write_all(...).await` and `flush().await` through one Compio writer. This preserves Crossterm and Ratatui compatibility while preventing terminal writes from blocking the runtime thread.

The quickest sound first version should adapt, rather than fork, Crossterm's existing reader:

1. drain `crossterm::event::poll(Duration::ZERO)` and `read()` while Crossterm already has a buffered event;
2. otherwise await `PollFd::read_ready()` on the same terminal input source;
3. return to step 1, letting Crossterm own byte reads and parsing.

Crossterm promises that `read` will not block after `poll` returns `true`, and its reader keeps parsed events in an internal queue ([public polling contract](https://github.com/crossterm-rs/crossterm/blob/a2a4523ddd37dcbd7e17bda973efbca3e5ad6125/src/event.rs), [reader queue](https://github.com/crossterm-rs/crossterm/blob/a2a4523ddd37dcbd7e17bda973efbca3e5ad6125/src/event/read.rs)). Draining first is essential: one kernel read can decode several events, after which the fd is no longer readable even though Crossterm still has events.

This bridge is appropriate for the experiment, but it is not the final deep module. Crossterm's event source, parser, internal events, and filterable reader are all crate-private. Its Unix parser covers UTF-8, legacy and CSI-u keyboard input, focus, several mouse encodings, bracketed paste, cursor replies, and keyboard-capability replies, so replacing it correctly is substantial ([Unix parser](https://github.com/crossterm-rs/crossterm/blob/a2a4523ddd37dcbd7e17bda973efbca3e5ad6125/src/event/sys/unix/parse.rs), [internal event boundary](https://github.com/crossterm-rs/crossterm/blob/a2a4523ddd37dcbd7e17bda973efbca3e5ad6125/src/event/internal.rs)). The durable options are to extract that parser with provenance into `compio-term`, or upstream a public parser/source seam to Crossterm. Calling Crossterm after Compio readiness is preferable to an incomplete parser in the first slice.

## Unix source and resize behavior

Match Crossterm's terminal-source selection exactly: use standard input when it is a TTY, otherwise open `/dev/tty`. Crossterm makes that choice before registering the descriptor with Mio ([TTY descriptor selection](https://github.com/crossterm-rs/crossterm/blob/a2a4523ddd37dcbd7e17bda973efbca3e5ad6125/src/terminal/sys/file_descriptor.rs), [Unix Mio source](https://github.com/crossterm-rs/crossterm/blob/a2a4523ddd37dcbd7e17bda973efbca3e5ad6125/src/event/source/unix/mio.rs)). A local macOS pseudo-TTY probe confirmed the reason to preserve this detail: polling a separately opened `/dev/tty` failed with `EINVAL`, while `/dev/stdin` worked when stdin was a TTY. The same probe decoded a character and a combined Up-arrow-plus-character input after buffered events were drained first.

Linux and macOS can share this high-level source and parser. Linux may use io_uring while macOS uses Compio's poll driver; `PollFd` hides that difference. Do not make the descriptor nonblocking merely to drain it: changing `O_NONBLOCK` on a duplicated descriptor can affect the shared open-file description. Await readiness and leave the actual read to Crossterm in the bridge. If `compio-term` later owns reads, it should have exclusive ownership, perform one bounded read per readiness notification, preserve partial parser state, and treat EOF as terminal closure rather than spinning.

TTY readiness does not cover resize. Crossterm registers both the TTY and a `SIGWINCH` signal source, then queries the new size when the signal becomes readable ([Unix Mio source](https://github.com/crossterm-rs/crossterm/blob/a2a4523ddd37dcbd7e17bda973efbca3e5ad6125/src/event/source/unix/mio.rs)). The implemented Unix adapter registers a signal-hook self-pipe for `SIGWINCH` and wraps its read end in a second `PollFd`. It drains that pipe only as a wake source, then returns to Crossterm's zero-duration poll so Crossterm remains the single owner of resize decoding and size queries. Repeated signals are naturally coalesced by the bounded pipe drain. Compio 0.19.1 also has a Unix signal future, but it installs its own process signal handler; combining that casually with Crossterm's signal-hook registration risks competing ownership ([Compio Unix signal source](https://github.com/compio-rs/compio/blob/13d847631b7b43ad00ba9253e22acfc8d49f2664/compio-signal/src/unix/mod.rs)). Using signal-hook for both registrations avoids installing a competing signal handler. A future fully owned parser backend should query size directly with `TIOCGWINSZ`; Crossterm's fallback can launch `tput`, which is inappropriate inside the single runtime thread ([Crossterm Unix terminal implementation](https://github.com/crossterm-rs/crossterm/blob/a2a4523ddd37dcbd7e17bda973efbca3e5ad6125/src/terminal/sys/unix.rs)).

## Recommended experimental API boundary

Expose one small, single-consumer `EventStream` wrapper. Its concrete shape is `EventStream(sys::EventStream)`: the public layer delegates `Stream` and `FusedStream`, while `sys::unix` owns `PollFd`, signals, and platform descriptors. Mutable stream polling makes exclusive event ownership visible and prevents concurrent waiters from racing the terminal queue. Initially return Crossterm's public event types so Intuigram and Ratatui integration do not need another translation layer ([public event model](https://github.com/crossterm-rs/crossterm/blob/a2a4523ddd37dcbd7e17bda973efbca3e5ad6125/src/event.rs)).

The bridge must document that no caller may also use `crossterm::event::read`, `poll`, or `EventStream`. Cursor-position and keyboard-capability queries also consume Crossterm's private global reader, so they must eventually become requests routed through the same `EventReader`, not independent blocking calls ([cursor-position query](https://github.com/crossterm-rs/crossterm/blob/a2a4523ddd37dcbd7e17bda973efbca3e5ad6125/src/cursor/sys/unix.rs), [keyboard-capability query](https://github.com/crossterm-rs/crossterm/blob/a2a4523ddd37dcbd7e17bda973efbca3e5ad6125/src/terminal/sys/unix.rs)).

## Follow-up: asynchronous terminal output (2026-08-03)

Making Crossterm's `Command` itself asynchronous is the wrong seam. In Crossterm 0.29, `Command::write_ansi` synchronously formats UTF-8 into `fmt::Write`; `queue` adapts each formatted string chunk to `io::Write::write_all`, while `execute` is only `queue` followed by `flush` ([Crossterm command implementation](https://github.com/crossterm-rs/crossterm/blob/36d95b26a26e64b0f8c12edfe11f410a6d56a812/src/command.rs)). The formatting contract is intentionally synchronous and requires each `write_str` call to accept the complete string or fail ([Rust `fmt::Write`](https://doc.rust-lang.org/std/fmt/trait.Write.html)). There is no useful suspension point while producing an escape sequence; the potentially waiting operation is committing the resulting bytes to the terminal.

The recommended output boundary is therefore approximately `TerminalWriter::queue(command)` plus `TerminalWriter::present().await`. `queue` writes ANSI into a private `Vec<u8>` adapter implementing `fmt::Write`. `present` takes ownership of that complete batch, passes it to Compio's `AsyncWriteExt::write_all`, retrieves the same owned buffer from `BufResult`, clears it, and retains its allocation for the next frame. Compio's `AsyncWrite` deliberately transfers buffer ownership into each operation, and `write_all` handles partial writes while returning the buffer ([Compio `AsyncWrite`](https://github.com/compio-rs/compio/blob/13d847631b7b43ad00ba9253e22acfc8d49f2664/compio-io/src/write/mod.rs), [`write_all`](https://github.com/compio-rs/compio/blob/13d847631b7b43ad00ba9253e22acfc8d49f2664/compio-io/src/write/ext.rs)). The crate would enable Compio's `fs` feature locally to obtain its owned-buffer stdout and I/O traits; the existing `runtime`-only dependency is sufficient for `PollFd` input but does not expose this output surface ([Compio feature graph](https://github.com/compio-rs/compio/blob/13d847631b7b43ad00ba9253e22acfc8d49f2664/compio/Cargo.toml)). Call `flush().await` after the batch to honor arbitrary buffered writers even though the resolved Compio stdout implementations themselves currently use an unbuffered writer and a no-op flush ([Compio stdout API](https://github.com/compio-rs/compio/blob/da39e71278af6ad636aa63fe21ca27aa50e9ab49/compio-fs/src/stdio/mod.rs), [Unix stdout](https://github.com/compio-rs/compio/blob/da39e71278af6ad636aa63fe21ca27aa50e9ab49/compio-fs/src/stdio/unix.rs)).

One object or task must exclusively own stdout and preserve batch order. Do not spawn one write per command or frame: Compio documents that only an individual stdout write is kept intact, while `write_all` may require several writes and can interleave with another writer ([Compio stdout API](https://github.com/compio-rs/compio/blob/da39e71278af6ad636aa63fe21ca27aa50e9ab49/compio-fs/src/stdio/mod.rs)). Batching all cursor movement, style changes, cell text, and optional begin/end-synchronized-update commands into one buffer minimizes submissions and gives the terminal one ordered frame. Awaiting that batch yields the single-threaded runtime so input and adapter tasks remain runnable.

Ratatui 0.30.2 does not currently provide an asynchronous backend contract: `Backend::draw` and `Backend::flush` are synchronous, and `CrosstermBackend<W: Write>` queues Crossterm commands into that synchronous writer ([Ratatui `Backend`](https://github.com/ratatui/ratatui/blob/e665c36cb14752a61cd777fbd06dbef8474f2add/ratatui-core/src/backend.rs), [`CrosstermBackend`](https://github.com/ratatui/ratatui/blob/e665c36cb14752a61cd777fbd06dbef8474f2add/ratatui-crossterm/src/lib.rs)). The practical adapter is a `CrosstermBackend` backed by the reusable in-memory writer, followed by one asynchronous presentation step. Normal `Terminal::draw` swaps Ratatui's comparison buffers before returning, however, so it would treat the frame as presented before the Compio write succeeds ([Ratatui render sequence](https://github.com/ratatui/ratatui/blob/e665c36cb14752a61cd777fbd06dbef8474f2add/ratatui-core/src/terminal/render.rs)). The experimental integration should either wrap Ratatui's low-level render, diff, cursor, and buffer-swap steps so the swap commits only after a successful write, or explicitly invalidate the previous frame and force a full redraw after an output failure.

Cancellation is not a frame transaction. A cancelled or failed `write_all` may already have emitted a prefix, and Compio documents that cancellation of a submitted operation is not reliable ([Compio cancellation](https://github.com/compio-rs/compio/blob/d7387fc16e143ded604b7c18ea3c1e95745028aa/compio-driver/src/lib.rs), [submission future](https://github.com/compio-rs/compio/blob/d7387fc16e143ded604b7c18ea3c1e95745028aa/compio-runtime/src/future/future.rs)). Do not cancel a frame after presentation begins; await it during orderly shutdown. On failure, assume terminal state is unknown, close any synchronized update and restore cursor/style state best-effort, then perform a full redraw. Blindly retrying the entire byte buffer can duplicate printable content.

This asynchronous-output design remains research only; the current thin event adapter intentionally leaves Crossterm commands and Ratatui presentation synchronous.

Terminal queries need a wider session API rather than an async `Command`. Cursor-position and capability queries must first present their request, then await and filter a response through the sole event reader while retaining unrelated input. A `TerminalSession` owning both ordered output and the single-consumer `EventReader` makes that protocol explicit.

On Windows, ANSI output through Compio is workable when virtual-terminal sequences are supported. Preserving Crossterm's legacy-console semantics is a separate backend problem: Crossterm may bypass ANSI and invoke a direct WinAPI method, while Compio's console `Stdout` submits ordinary `std::io::Write` as a blocking operation rather than an overlapped console write ([Crossterm command implementation](https://github.com/crossterm-rs/crossterm/blob/36d95b26a26e64b0f8c12edfe11f410a6d56a812/src/command.rs), [Compio Windows stdout](https://github.com/compio-rs/compio/blob/da39e71278af6ad636aa63fe21ca27aa50e9ab49/compio-fs/src/stdio/windows.rs)). The experiment should state an ANSI-capable terminal requirement instead of pretending an asynchronous ANSI adapter preserves every legacy WinAPI command.

## Remaining Crossterm capability families

| Family                                                               | Direction                                                 | Reason                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| -------------------------------------------------------------------- | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Raw mode                                                             | Thin RAII wrapper over Crossterm                          | The termios operation is synchronous setup/teardown, not event waiting; reuse it and guarantee restoration on drop.                                                                                                                                                                                                                                                                                                                                                 |
| Alternate screen, style, clearing, cursor movement/visibility, title | Reuse command encoders through an async batch presenter   | Encode commands synchronously into one reusable frame buffer, then perform one ordered Compio `write_all` and `flush`; do not make each command asynchronous.                                                                                                                                                                                                                                                                                                       |
| Terminal size                                                        | Thin wrapper now; direct ioctl later                      | Ordinary queries can reuse Crossterm, but the runtime-safe resize path should avoid its blocking `tput` fallback.                                                                                                                                                                                                                                                                                                                                                   |
| Cursor position                                                      | Integrated async request later                            | Movement commands are reusable; the position query writes a terminal request and filters a response from the same input queue.                                                                                                                                                                                                                                                                                                                                      |
| Keyboard enhancement                                                 | Reuse push/pop commands; integrate detection later        | Enabling is an ANSI command, while detection is a request/response exchange on the event reader.                                                                                                                                                                                                                                                                                                                                                                    |
| Focus, mouse, bracketed paste                                        | Reuse enable/disable commands; bridge or duplicate parser | Their input is encoded in the same terminal byte stream and already represented by Crossterm's public `Event` model.                                                                                                                                                                                                                                                                                                                                                |
| Windows console                                                      | Future platform backend                                   | Crossterm reads Win32 console input records rather than a Unix TTY byte stream, and Compio's Windows `PollFd` readiness implementation is socket-oriented ([Crossterm Windows source](https://github.com/crossterm-rs/crossterm/blob/a2a4523ddd37dcbd7e17bda973efbca3e5ad6125/src/event/source/windows.rs), [Compio Windows `PollFd`](https://github.com/compio-rs/compio/blob/d7387fc16e143ded604b7c18ea3c1e95745028aa/compio-runtime/src/fd/poll_fd/windows.rs)). |
