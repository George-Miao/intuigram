# Durable Outbox execution

Every outbound Message send, media send, Scheduled Message operation, and existing-Message mutation is admitted to the Account database before Telegram execution. Admission atomically stores a versioned Intuigram-owned semantic command, its stable Telegram random ID, exact referenced media bytes and hashes, any optimistic Message, and scoped Draft consumption. A retained main-runtime coordinator claims one FIFO head, while the Account's dedicated Telegram actor performs only that item's upload or invocation. Telegram-returned updates commit through the ordered update driver before the Outbox completion transaction removes the item and replaces optimistic records.

Flood waits and invocation-capacity saturation defer the FIFO head to an explicit timestamp. Connection failures replay random-ID-safe sends and creates after reconnection, but move replay-unsafe mutations to an unknown-outcome state. Definite mutation failures require conflict resolution; local corruption fails without remote execution. Cancellation marks unstarted work cancelled, records a request while work is active, and never claims an ambiguous connection failure was unsent. Explicit deadlines become visible expiry states. Startup recovery returns interrupted sends and creates to ready state while preserving their identity and media, and moves interrupted mutations or cancellations to unknown outcome. This serializes outbound operations and retains media bytes in SQLite until resolution, increasing storage and head-of-line latency in exchange for restart safety, deterministic ordering, and explicit user control over ambiguous outcomes.
