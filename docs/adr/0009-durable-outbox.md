# Durable Outbox execution

Before Telegram execution, Intuigram admits each outbound Message send, media send, Scheduled Message operation, and existing-Message mutation to the Account database. Admission atomically stores a versioned Intuigram-owned semantic command. It also stores the stable Telegram random ID, exact referenced media bytes and hashes, each optimistic Message, and scoped Draft consumption. A retained coordinator on the main runtime claims one FIFO head. The dedicated Telegram actor of the Account uploads or invokes only this item. The ordered update driver commits updates returned by Telegram. Then the Outbox completion transaction removes the item and replaces optimistic records.

Flood waits and invocation-capacity saturation defer the FIFO head to an explicit time. After reconnection, Intuigram replays sends and creates that are safe because they use random IDs. It moves replay-unsafe mutations to an unknown-outcome state. Definite mutation failures require conflict resolution. Local corruption causes failure without remote execution. Cancellation marks work that did not start as cancelled. If work is active, cancellation records a request. It never states that an ambiguous connection failure did not send the operation. Explicit deadlines become visible expiry states. Startup recovery returns interrupted sends and creates to the ready state. It preserves their identity and media. It moves interrupted mutations or cancellations to unknown outcome. This design serializes outbound operations. It keeps media bytes in SQLite until resolution. Thus, it increases storage use and head-of-line latency. In return, it provides restart safety, deterministic ordering, and explicit user control of ambiguous outcomes.
