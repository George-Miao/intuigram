# Workspace crates

Intuigram is a virtual Cargo workspace whose packages all live under `crates/`. Intuigram-specific packages use the `intuigram-*` prefix, while genuinely reusable utilities use independent names. The crate seams are `intuigram` for the minimal executable entrypoint, `intuigram-app` for executable orchestration and concrete adapter composition, `intuigram-lib` for canonical application state and use-case interfaces, `intuigram-tui` for terminal interaction and presentation, `intuigram-telegram` for Telegram synchronization and protocol adaptation, `intuigram-store` for durable local records, `intuigram-media` for media transfer and cache policy, `intuigram-config` for layered configuration, `compio-mtproto` for reusable MTProto transport and raw invocation, `compio-actor` for experimental typed actors on Compio dispatcher workers, `compio-term` for Compio-native terminal readiness, `rasterm` for reusable terminal raster detection, geometry, protocol encoding, external-renderer commands, and image lifecycle, `rich-clipboard` for platform clipboard content, and the dev-only `test-harness` for hermetic cross-layer behavior scenarios. The actor crate is vendored while it is co-developed and keeps its interface independent of Intuigram; `intuigram-app` alone adapts its mailbox and lifecycle primitives to the Telegram-session seam. `rasterm` owns no terminal UI or product model and accepts owned RGBA images plus cell placements rather than Ratatui or Intuigram values. `intuigram-lib` solely owns canonical application state and its transitions. The TUI submits typed user intents and renders read-only view data; Telegram, storage, and media adapters submit typed events. Ratatui widgets, Telegram TL values, database rows, actor mailboxes, and other adapter-specific types never cross the `intuigram-lib` interface. Domain-facing dependencies point toward `intuigram-lib`; adapter crates do not depend on `intuigram-app`, `intuigram-app` composes the adapters, and `intuigram` depends only on `intuigram-app`. `test-harness` depends on the production composition and state crates, while `intuigram-app` includes it only as a dev-dependency; this test-only dependency cycle does not enter production builds. This creates independent test surfaces and reusable modules at the cost of more packages and explicit interfaces. New crates require a demonstrated seam and meaningful hidden behavior rather than merely grouping related types.
