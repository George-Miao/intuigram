# Single-writer state

`intuigram-app` exclusively owns mutable application state and exposes a synchronous reducer that applies one typed user intent or adapter event in deterministic order, returning an immutable view and at most one adapter effect. The `intuigram` composition loop runs that reducer, terminal input, rendering, Telegram, and nonblocking adapters on one Compio runtime thread. It polls persistent sources and an explicitly bounded effect queue in place; waking for terminal input does not cancel and recreate an in-flight Compio operation. Poll priority rotates after every ready source so a sustained stream of Telegram updates, terminal input, backend completions, or animation frames cannot starve the other sources. Blocking SQLite work remains on dedicated database threads. No adapter exposes shared mutable state or requires cross-crate locking. Effect enqueueing never waits for capacity: saturation is surfaced as an error. Chat-history requests allow one in-flight load and coalesce further navigation to the latest pending Chat, so stale foreground work cannot build an input-blocking queue. Root-Chat history warmup walks the known Chat directory through a fixed cursor rather than enqueueing every Chat; each completion gives the latest foreground request priority before continuing the next background load. Each load requests one bounded recent page and yields before older history is requested incrementally, so opening one large Chat cannot monopolize the backend. This makes update, optimistic-action, acknowledgement, selection, and Draft ordering testable through the `intuigram-app` interface at the cost of explicit polling, backpressure, and shutdown design.
