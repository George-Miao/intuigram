# Telegram client ownership

Intuigram does not use `grammers-client`, `grammers-mtsender`, or `grammers-session`. Their high-level model omits Telegram behavior Intuigram requires, their sender exposes no transport seam, and their built-in storage conflicts with a single mature SQLite stack. The reusable `compio-mtproto` crate owns completion-based connections, authentication-key negotiation, MTProto session mechanics, request correlation, acknowledgements, bounded retries, connection-failure classification, and an update stream behind a raw invocation interface. Its route layer also owns SOCKS5 and HTTP CONNECT negotiation, MTProxy obfuscation and transport selection, bounded connection attempts, and ordered direct fallback; credentials and secrets remain typed redacted values. `intuigram-telegram` validates each candidate through MTProto key exchange and Telegram API initialization before accepting it, so a transport-only handshake cannot prevent fallback. It also owns login, data-center selection, raw Telegram requests, scoped Account and Channel update normalization, and gap detection; `intuigram-app` maps layered user configuration into the reusable route policy and reconciles a gap or transport failure through a fresh bootstrap before resuming live updates. A live client is constructed inside a dedicated one-worker `compio-actor` cluster and never crosses back to the main thread. The actor retains a worker-local `LiveUpdates` driver task so MTProto invocations continue to make progress while the serial command handler awaits their replies. Its bounded mailbox accepts only Intuigram-owned effects, peer data, and attachment payloads needed by an admitted send; its bounded output publishes only normalized adapter batches and explicit failure categories. Native clipboard reads, attachment validation and byte reads, media capture, platform launching, media decoding, cache access, and download writes remain outside that mailbox; the actor receives owned upload bytes only after local preparation. Preview and download RPCs return Telegram-owned bytes to those local adapters. An RPC-returned update is handed to the worker-local durability coordinator, which snapshots and drains the older buffered live-envelope prefix before publishing every committed event on the one ordered driver channel and acknowledging the actor call. Later continuous live traffic cannot extend that barrier or starve the acknowledgement. A reserved cancellation signal can interrupt connection setup or a flood-waiting command without depending on mailbox capacity; closing the driver wakes any pending commit waiter, and orderly shutdown then awaits the actor and joins the cluster. Terminal notifications, external-link launching, and typed Draft and selection persistence likewise remain main-runtime effects. Intuigram initially retains mature low-level grammers TL generation, MTProto codec, and cryptographic crates rather than rewriting protocol schema generation or cryptography. The grammers sender implementation and Telegram's transport specification remain behavioral references for protocol state transitions and framing, but do not define Intuigram's interface or runtime design. This provides complete API coverage, thread isolation, and a coherent Compio runtime at the substantial cost of maintaining Telegram client behavior, actor lifecycle coordination, and protocol conformance.
