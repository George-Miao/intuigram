# Telegram client ownership

Intuigram does not use `grammers-client`, `grammers-mtsender`, or `grammers-session`. Their high-level model omits Telegram behavior Intuigram requires, their sender exposes no transport seam, and their built-in storage conflicts with a single mature SQLite stack. The reusable `compio-mtproto` crate owns completion-based connections, authentication-key negotiation, MTProto session mechanics, request correlation, acknowledgements, bounded retries, connection-failure classification, and an update stream behind a raw invocation interface. Its route layer also owns SOCKS5 and HTTP CONNECT negotiation, MTProxy obfuscation and transport selection, bounded connection attempts, and ordered direct fallback; credentials and secrets remain typed redacted values. `intuigram-telegram` validates each candidate through MTProto key exchange and Telegram API initialization before accepting it, so a transport-only handshake cannot prevent fallback. It also owns login, data-center selection, raw Telegram requests, scoped Account and Channel update normalization, and gap detection; the executable maps layered user configuration into the reusable route policy and reconciles a gap or transport failure through a fresh bootstrap before resuming live updates. Intuigram initially retains mature low-level grammers TL generation, MTProto codec, and cryptographic crates rather than rewriting protocol schema generation or cryptography. The grammers sender implementation and Telegram's transport specification remain behavioral references for protocol state transitions and framing, but do not define Intuigram's interface or runtime design. This provides complete API coverage and a coherent Compio runtime at the substantial cost of maintaining Telegram client behavior and protocol conformance.
