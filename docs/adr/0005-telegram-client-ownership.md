# Telegram client ownership

Intuigram does not use `grammers-client`, `grammers-mtsender`, or `grammers-session`. Their high-level model does not include the Telegram behavior that Intuigram requires. Their sender does not provide a transport seam. Their built-in storage conflicts with one mature SQLite stack. The reusable `compio-mtproto` crate owns completion-based connections, authentication-key negotiation, MTProto session mechanics, bounded request correlation, acknowledgements, retries, connection-failure classification, and passive updates. It provides these functions through a raw invocation interface. It uses the mature low-level grammers TL, codec, and cryptographic crates. Intuigram does not rewrite Telegram cryptography. The route layer owns SOCKS5 and HTTP CONNECT negotiation, MTProxy obfuscation and transport selection, bounded connection attempts, and ordered direct fallback. `intuigram-telegram` validates each candidate through MTProto key exchange and Telegram API initialization before it accepts the candidate. It then owns login, data-center selection, raw requests, update normalization, and gap detection.

Intuigram constructs a live client in a dedicated one-worker cluster with the upstream Compio actor API. The client never crosses back to the main thread. The actor keeps a worker-local `LiveUpdates` driver. Thus, multiple correlated invocations and passive updates can make progress together. Flood waits and cancellation apply to individual invocations. Mailbox capacity and invocation capacity are bounded. Actor output contains only normalized adapter batches and explicit failure categories. The MTProto driver keeps the producing request with each correlated own update until normalization assigns the correct Account or Channel cursor scope. It never logs this request because it can contain private user data. For an update returned by an RPC, the actor gives the update to the worker-local durability coordinator. The coordinator takes a snapshot and drains the older prefix of buffered live envelopes. It then publishes committed events and acknowledges the call. Later continuous traffic cannot extend this barrier or prevent the acknowledgement. A reserved cancellation signal can stop connection setup or a command that waits for a flood delay. This signal does not depend on mailbox capacity.

Intuigram keeps Account-owned media sessions for each data center. These sessions are separate from ordinary control traffic. Intuigram imports cross-DC authorization one time for each retained session. It prefers media-only endpoints when Telegram advertises them. It can fetch aligned file parts concurrently under bounded byte admission and active-file admission. Ordered assembly occurs outside the UI loop. Normalized file locations contain sufficient identity to select thumbnails without another Message request. They can also refresh expired file references. CDN redirects use the current Telegram CDN RSA keys and the same low-level grammers cryptographic primitives. Intuigram then decrypts offset-aware AES-CTR parts, verifies Telegram hashes, requests reupload through the origin data center, and uses fallback behavior when a CDN token is invalid. A reconnect removes or rebuilds the affected media sessions as one coherent operation.

Native clipboard reads, attachment validation and byte reads, media capture, platform launch work, media decoding, cache access, and download writes stay outside the Telegram actor. The actor receives owned upload bytes only after local preparation. During an orderly shutdown, Intuigram waits for the actor and joins the cluster after durable updates commit. This design provides complete API coverage, thread isolation, and one coherent Compio runtime. The cost is the maintenance of Telegram client behavior, actor lifecycle coordination, and protocol conformance.
