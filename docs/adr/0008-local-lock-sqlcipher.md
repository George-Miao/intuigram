# Local Lock uses full Account-database encryption

Optional Local Lock encrypts the complete SQLite database of each Account with SQLCipher. Encryption occurs before schema inspection, migration, or ordinary access. It protects Telegram authorization material, synchronization cursors, Chat metadata, Message text, Drafts, and other Local Records through the existing Account isolation seam. `global.db` stores only the non-secret Account directory. Redownloadable Media Cache bytes continue to use the cache lifecycle policy. Intuigram converts existing plaintext Account databases and their retained migration or recovery backups with `sqlcipher_export`. It validates each converted database with the selected key. It installs the converted database atomically. Only then does it remove the plaintext migration workspaces.

Local Lock derives the unlock key with PBKDF2-SHA-256 from a hidden passphrase and a random owner-only salt for each Account. As an alternative, it uses a random 256-bit value that it stores in the native OS credential vault. Intuigram promotes pending-login salt and keyring entries only after it can reopen the encrypted Account. If promotion stops unexpectedly, Intuigram recovers from the pending material. It does not generate a new key. Accounts encrypted before Intuigram added per-Account salts continue to use the legacy derivation. They keep this derivation until an explicit rekey migration is available. An initial passphrase requires confirmation. Secrets and raw keys use zeroizing memory. Diagnostics redact database keys. Keyring calls occur during startup before Account storage or terminal interaction starts. This design increases binary size and migration complexity. It prevents partial field encryption from exposing new columns or leaving authorization material outside the protected boundary.
